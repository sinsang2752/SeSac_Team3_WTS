# ADR-0011: `processed_events` 테이블을 두지 않는다

- 상태: 채택
- 날짜: 2026-09-22
- 관련: CLAUDE.md §17, §23, §52 / Phase 4

## 맥락

§17은 Consumer가 `eventId` 기준으로 중복 처리를 막으라고 하고, §23은 그 용도로
`processed_events(event_id, consumer_name, processed_at)` 테이블을 제시한다.

Phase 4의 Consumer는 하나다. `market.price.updated`를 받아 미체결 지정가 주문을 체결한다.

## 결정

이 테이블을 만들지 않는다. 중복 방지는 **주문 상태 머신**이 한다.

## 이유

체결은 `Order.fill()`을 거치고, `fill()`은 상태가 `ACCEPTED`일 때만 통과한다.
같은 시세 이벤트가 두 번 와도 두 번째에는 주문이 이미 `FILLED`라 그냥 넘어간다.

이건 eventId 기반 중복 제거보다 **더 강한 보장**이다. eventId 방식은 "같은 이벤트를 두 번
처리하지 않는다"만 보장한다. 주문 상태는 여기에 더해 "서로 다른 두 이벤트가 같은 주문을
두 번 체결하지 않는다"까지 보장한다. 시세가 1초마다 오는 환경에서는 후자가 실제로 일어나는
경우다.

비용도 고려했다. `market.price.updated`는 종목당 초당 한 건이다. 5종목이면 하루 43만 건이고,
모두 dedup 행을 남기면 정리 작업이 필요한 테이블이 하나 더 생긴다. 얻는 것이 없다.

## 이 결정이 뒤집히는 시점

**이벤트 payload 자체가 상태 변경의 근거가 되는 Consumer**가 생기면 그때는 필요하다.
예를 들어 다른 서비스의 `execution.completed`를 받아 통계를 누적하는 소비자는 같은 이벤트를
두 번 받으면 값이 부풀고, 자기 상태만으로는 중복인지 알 수 없다.

Phase 2의 1분봉 집계도 같은 문제를 다른 방법으로 풀었다. 거래량을 증분이 아니라 **누적값**으로
발행해서 중복 수신이 집계를 부풀리지 않게 했다. 두 경우 모두 "중복이 들어와도 결과가 같게"
설계한 것이지, dedup 테이블을 생략한 것이 아니다.
