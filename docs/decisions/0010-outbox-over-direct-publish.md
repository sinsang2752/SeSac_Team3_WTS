# ADR-0010: Kafka 발행은 Outbox를 거친다

- 상태: 채택
- 날짜: 2026-09-22
- 관련: CLAUDE.md §2, §15, §16 / Phase 4

## 맥락

체결이 일어나면 DB(주문·계좌·포지션·원장)가 바뀌고 Kafka 이벤트가 나가야 한다.
두 저장소에 쓰는 일을 한 트랜잭션으로 묶을 수 없다. Dual Write 문제다.

트랜잭션 안에서 바로 발행하면:

- 발행 성공 → 커밋 실패: 일어나지 않은 체결의 이벤트가 나간다. **되돌릴 수 없다.**
- 커밋 성공 → 발행 실패: 체결은 됐는데 아무도 모른다.

## 결정

거래 트랜잭션은 Kafka를 모른다. 이벤트를 `outbox_events`에 **같은 커밋으로** 적고,
별도 Publisher가 폴링해 브로커로 옮긴다 (§15).

`OutboxRecorder`는 `@Transactional(MANDATORY)`다. 트랜잭션 없이 부르면 즉시 실패한다.
별도 트랜잭션으로 적히면 Outbox를 쓰는 의미가 없어지기 때문이다.

## 결과

- **At-Least-Once.** Publisher가 Kafka 전송 후 커밋 직전에 죽으면 같은 메시지가 다시 나간다.
  그래서 `DomainEvent` 봉투 전체를 `payload_json`에 저장한다. 재발행해도 `eventId`가
  그대로여야 소비자가 중복을 걸러낼 수 있다 (§17).
  발행 시점에 봉투를 다시 만들면 eventId가 매번 달라져 중복 제거가 불가능해진다.
- Publisher는 **트랜잭션을 Kafka 전송이 끝날 때까지 들고 있다.** 잡은 행에 락이 걸린 채
  I/O를 하는 셈이라 배치를 100건으로 제한했다. 대신 "보냈는데 PUBLISHED로 못 적는" 창이 없다.
- `SELECT ... FOR UPDATE SKIP LOCKED`로 집는다. 인스턴스를 여러 개 띄워도 서로 다른 행을
  나눠 갖는다. 잠긴 행은 다음 폴링에서 다시 대상이 된다.
- 발행이 계속 실패하면 `retry_count`가 쌓이고 5회에서 `FAILED`가 된다. 계속 재시도하면
  뒤따르는 이벤트가 영원히 막히기 때문이다. 남은 행은 사람이 본다. DLQ는 MVP 후반이다 (§17).
- **이벤트에 지연이 있다.** 폴링 간격(기본 500ms)만큼 늦게 나간다.
  MVP에서 이 지연을 신경 쓰는 소비자는 없다. CDC/Debezium은 §15가 "MVP 필수가 아니다"라고
  명시했다.
